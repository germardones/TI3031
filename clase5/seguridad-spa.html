Desarrollo Seguro en SPA

Una SPA corre en el navegador del usuario: todo tu código es público. Programar seguro no es opcional, es parte del oficio.

⚠ Regla #0: El frontend nunca es de confianza

El usuario puede ver y modificar todo tu JavaScript con F12. Cualquier validación importante o secreto debe estar en el servidor (backend), nunca solo en React. El frontend valida para la experiencia; el backend valida para la seguridad.

1. XSS (Cross-Site Scripting)

El XSS es la amenaza #1 en SPAs: un atacante inyecta scripts que se ejecutan en el navegador de otros usuarios (robando sesiones, datos, etc.).

✓ Buena noticia: React te protege por defecto

Cuando muestras datos con { }, React los escapa automáticamente. Un script inyectado se muestra como texto, no se ejecuta.

const comentario = "<script>robar()</script>";

// React lo muestra como TEXTO, seguro ✓
return <p>{comentario}</p>;

✗ El peligro: dangerouslySetInnerHTML

Esta propiedad inserta HTML sin escapar. Su nombre lleva "dangerously" a propósito. Si lo usas con datos del usuario, abres la puerta al XSS.

// ❌ PELIGRO: ejecuta cualquier HTML/script
<div dangerouslySetInnerHTML={{ __html: comentario }} />

// Si lo necesitas, limpia antes con DOMPurify:
import DOMPurify from "dompurify";
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(comentario) }} />

2. Tokens, Claves y Secretos

Todo lo que pongas en el código de React viaja al navegador y es visible. Las claves secretas (de bases de datos, de pago) jamás van en el frontend.

✗ Nunca hagas esto
// Cualquiera ve esta clave con F12
const API_SECRET = "sk_live_a8f7...";
fetch(url, {
  headers: { Authorization: API_SECRET }
});
✓ Variables de entorno (Vite)

Para config no secreta (URL base). Archivo .env, prefijo VITE_:

# archivo .env
VITE_API_URL=https://api.midominio.com

// en el código:
const url = import.meta.env.VITE_API_URL;

⚠ Las variables VITE_ TAMBIÉN son públicas

El archivo .env evita escribir valores "a mano" en el código, pero al compilar, esos valores quedan dentro del JavaScript que descarga el navegador. Sirven para configuración, no para secretos. Los secretos reales viven solo en el backend.

Y siempre agrega .env a tu .gitignore para no subirlo a GitHub.

3. Sesiones y Almacenamiento

¿Dónde guardar el token de sesión del usuario? Esto conecta con lo que viste en Local Storage.

Dónde Riesgo Recomendación
localStorage Accesible por cualquier JS → vulnerable a XSS Evitar para tokens
Cookie httpOnly El JavaScript no puede leerla Preferida (la pone el backend)

Una cookie httpOnly la crea y lee el servidor; el JavaScript del navegador no la toca. Por eso es la opción segura para tokens de sesión. localStorage úsalo para preferencias no sensibles (tema, idioma).

4. Checklist de Seguridad

Revisa esta lista antes de publicar cualquier SPA:

✅

Validar los datos del usuario en el backend, no solo en React.

✅

Evitar dangerouslySetInnerHTML; si lo usas, sanitiza con DOMPurify.

✅

Nunca poner claves secretas en el código del frontend.

✅

Tokens de sesión en cookies httpOnly, no en localStorage.

✅

Usar siempre HTTPS para cifrar el tráfico.

✅

Mantener dependencias al día: npm audit detecta vulnerabilidades.

✅

Agregar .env al .gitignore.

✅

Pasar SonarLint para detectar problemas de seguridad.
